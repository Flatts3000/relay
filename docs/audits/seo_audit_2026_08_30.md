# SEO audit, 2026-08-30

**Scope:** the public web surface of relayfunds.org. Six application routes and
the four static marketing pages added in #78.

**Input:** the standing checklist at `~/.claude/rules/common/seo_audit_checklist.md`
(SC-1 through SC-35). This is the first SEO audit on this repository, so there is
no prior audit to diff against.

**Method.** Playwright against the real production build: application routes and
static pages both served by `deploy/nginx.prod.conf` from `frontend/dist`, with
`/api` proxied to a live backend and a seeded database. Core Web Vitals measured
at 390x760, which is Google's primary crawler viewport. Header and redirect
behavior read off a real nginx container rather than inferred from the config.

## CRITICAL

### S-1: Every application route declares itself a copy of the home page

**File:** `frontend/index.html:20`
**Checklist:** SC-5, SC-7
**Risk:** the highest-impact finding in this audit.

`frontend/index.html` is one template serving every SPA route, and #78 added
Open Graph tags to it with a hardcoded `og:url`:

```html
<meta property="og:url" content="https://relayfunds.org/" />
```

Measured, five routes serve that tag while being served at a different URL:

```
/directory declares og:url https://relayfunds.org/
/login     declares og:url https://relayfunds.org/
/privacy   declares og:url https://relayfunds.org/
/security  declares og:url https://relayfunds.org/
/terms     declares og:url https://relayfunds.org/
```

All six also share one `meta description`, verbatim, and none carries
`rel="canonical"`.

To a crawler this is five URLs each announcing that its canonical identity is
`/`. That is a self-inflicted duplicate-content signal on the entire application,
including `/directory`, which is the one application route the product actually
wants found: the whole premise of the public directory is that community members
can discover local groups without an account.

`/security` is 828 words of substantive, unique content that currently cannot
rank for anything, because it tells Google it is the home page.

**This is partly a regression introduced by #78.** Before it, these routes had no
Open Graph tags at all, which was worse for sharing and better for canonical
integrity. The fix is to finish the job rather than revert.

**Remediation:**

1. Set per-route `<title>`, `meta description`, `link rel=canonical` and `og:url`
   at runtime. `DocumentTitle` in `App.tsx` already does this for `<title>`, so
   the hook and the route table exist; extend it to the other four tags.
2. Delete the hardcoded `og:url` from `frontend/index.html` or make it a default
   that the per-route code always overwrites.
3. Note the ceiling: this is client-side, so it works for Google, which renders
   JavaScript, and not for most social unfurlers, which do not. Truly robust
   per-route metadata needs prerendering. Given that `/directory` is the only
   application route with real SEO value, prerendering just that one is a
   proportionate option.
4. Verify by fetching each route and asserting `og:url` matches the request path.

## HIGH

### S-2: Every nonexistent URL returns HTTP 200

**File:** `deploy/nginx.prod.conf:62`, `frontend/nginx.conf`
**Checklist:** SC-1 adjacent

```
GET /no-such-page-xyz123  ->  200 OK, the application shell
GET /llms.txt             ->  200 OK, the application shell
```

The SPA fallback `try_files $uri $uri/ /index.html` returns the app for
everything, so there is no 404 status anywhere on the site. The app renders a
not-found view client-side, but the HTTP status is success.

Google calls this a soft 404 and handles it badly: crawl budget is spent on
unlimited nonexistent URLs, and any mistyped or stale inbound link becomes an
indexable page whose content is the app shell. It also silently defeats
monitoring: nothing can alert on a 404 rate that is structurally zero.

It caught this audit out directly. `/llms.txt` returned 200 and looked like a
pass for SC-32 until the body was read and turned out to be the app.

**Remediation:**

1. Have the SPA's not-found route return a real 404. With no server rendering,
   the practical form is an nginx `location` that 404s paths which are known not
   to be application routes, or a prerendered `404.html` served with
   `error_page 404 /404.html;` for anything not matching a known route prefix.
2. At minimum, add `<meta name="robots" content="noindex">` to the client-side
   not-found view so the soft 404s do not get indexed.
3. Verify that `/no-such-page-xyz123` returns 404 and `/directory` still returns 200.

### S-3: `/directory` shifts 0.18 of layout on load, over the 0.1 threshold

**File:** `frontend/src/pages/GroupDirectoryPage.tsx`
**Checklist:** SC-16
**Measured on the production build at 390x760, with a live API and 12 seeded groups.**

| Page              | LCP    | CLS       |
| ----------------- | ------ | --------- |
| `/`               | 216 ms | 0.002     |
| **`/directory`**  | 168 ms | **0.178** |
| `/what-is-relay/` | 72 ms  | 0.018     |
| `/need-help/`     | 72 ms  | 0.058     |
| `/for-groups/`    | 68 ms  | 0.002     |
| `/for-funds/`     | 72 ms  | 0.056     |

LCP is excellent everywhere. CLS on `/directory` is 1.8x the 0.1 budget, and
Core Web Vitals is a ranking signal on the one route with organic search value.

The dominant shift is a single event of 0.149 at 197 ms:

```
FOOTER.bg-gray-50 border-t border-gray-200   top,height: 647,113  ->  0,0
```

The page paints its shell and footer while the fetch is still in flight, then the
results arrive and displace everything below them. A second shift of 0.028 moves
the filter and result grids by 28px.

**Remediation:**

1. Reserve the space. Render skeleton cards matching the real card height while
   loading, or set a `min-height` on the results container sized to the default
   page of results.
2. Reserve height for the result-count line as well; it is in the 0.028 shift.
3. Re-measure and confirm CLS is under 0.1 on the production build, not the dev
   server.

## MEDIUM

### S-4: No structured data anywhere

**Checklist:** SC-11, SC-12, SC-13, SC-14

Zero `application/ld+json` on all ten pages. Nothing to lose here, only
unclaimed ground, and for an organization whose credibility is the product this
is cheap to fix:

1. `Organization` in the root layout: `name`, `url`, `logo`, `description`,
   `sameAs` pointing at the GitHub repository. Renders on every page.
2. `FAQPage` is not currently applicable; no page renders a Q/A list. Do not
   invent one to earn the schema.
3. `BreadcrumbList` is not applicable either; there are no breadcrumbs.
4. `SoftwareApplication` is a poor fit and should be **skipped deliberately**.
   Relay is not a product being sold, there is no `offers.priceRange`, and the
   deck research in `docs/deck_audience_research.md` is explicit that positioning
   this as a SaaS product misreads the audience. `Organization` is the honest one.

### S-5: The home page title is five characters

**File:** `frontend/index.html:42`

`<title>Relay</title>`. "Relay" is an extremely common word, competing against
relay races, relay switches and relay servers. The page has 661 words of good
content and a title that describes none of it.

The four static pages average 68 characters and are well formed; the home page
should match.

**Remediation:** something in the shape of `Relay: mutual aid, connected` or
`Relay: connecting mutual aid groups with the funds that back them`, 50 to 60
characters, and unique per route once S-1 is fixed.

### S-6: `/directory` and `/directory/` both return 200

**Checklist:** SC-4

```
/directory   ->  200
/directory/  ->  200
```

Two URLs, identical content, no canonical to break the tie (S-1). The static
pages handle this correctly: `/for-groups` 301s to `/for-groups/`.

**Remediation:** pick one form and 301 the other, or resolve it through the
canonical tags added in S-1. The canonical alone is sufficient and is the
smaller change.

## LOW

### S-7: No `llms.txt`

**Checklist:** SC-32. Severity LOW per the checklist's current guidance.

There is no `/llms.txt`; the 200 it returns is the soft 404 in S-2.

Worth more here than the LOW suggests. Relay's audience includes people
researching whether it is safe to use, and its central claim is that every
assertion can be checked against public code. A short `llms.txt` pointing at the
repository, the four explainer pages and `docs/` is a few lines and is aimed at
exactly the tools that audience uses.

**Remediation:** add `frontend/public/llms.txt` per `https://llmstxt.org/`,
generated by `marketing/build.mjs` so it cannot drift from the page set. Re-check
severity quarterly per the checklist's re-evaluation triggers.

### S-8: One share card for every application route

**Checklist:** SC-9

All six application routes share `/share/relay-<hash>.png`. Acceptable today and
strictly better than the nothing that existed before #78, but `/directory` and
`/security` would each benefit from their own. `marketing/build.mjs` already
generates per-page cards from a headline string; extending it is small.

## Fixed in this pass

### S-9: `sitemap.xml` claimed every page changed today, on every build

**File:** `marketing/build.mjs`
**Checklist:** SC-2, which asks for `lastModified` from real signals rather than
build time.

The sitemap stamped `new Date()` into every `<lastmod>`, so each rebuild
announced that all five URLs had just changed and produced a diff in every
commit that touched anything in `marketing/`. Crawlers discount a `lastmod` that
is always today, which costs the signal exactly when it would be useful.

Now derived from `git log -1 --format=%cI` for each page's own file, falling back
to today only for a path git does not know yet, which is accurate because an
uncommitted page really did just change. Verified idempotent: two consecutive
builds produce a byte-identical sitemap.

## What is strong

- **The four static pages pass essentially everything.** Unique titles of 60 to
  73 characters, unique descriptions of 157 to 185, correct canonicals, correct
  `og:url`, complete Open Graph and Twitter Card tags with real images on disk,
  one `h1` each, no heading-level skips, 875 to 1020 words of distinct content.
- **`robots.txt` is right, including the subtle part.** Auth-gated trees are
  disallowed (SC-27), the sitemap is referenced (SC-3), and `/deck` is
  deliberately _not_ disallowed so that its `X-Robots-Tag: noindex` can actually
  be seen. That reasoning is documented in the file itself.
- **No `Disallow` shadows a sitemap URL.** `/groups` does not prefix-match
  `/for-groups/`. Checked rather than assumed.
- **LCP is 68 to 216 ms across every page.** Nothing is close to the 2.5s budget.
- **The static pages load 98 KB over 6 requests with zero third-party
  requests.** The application loads 186 KB over 6 to 7 requests, which is also
  good, but it makes two third-party requests (see the security audit, and #80).
- **Every image has `alt`.** No exceptions on any page.
- **Heading hierarchy is clean everywhere.** No skipped levels on any of the ten
  pages (SC-22, SC-23).
- **Trailing-slash handling on the static pages is correct**, with a relative
  301 that does not downgrade the scheme.

## Priority order

1. **S-1** per-route canonical and `og:url`. Everything else about SPA
   indexability is downstream of this.
2. **S-2** real 404s. Cheap, and it is currently hiding problems from monitoring.
3. **S-3** `/directory` CLS. A ranking signal on the route that most needs to rank.
4. **S-5** home page title. Ten minutes.
5. **S-4** `Organization` JSON-LD.
6. **S-6** trailing slash, likely resolved by S-1.
7. **S-7** `llms.txt`, **S-8** per-route cards.
